# 1. Introducción
La Fase 2 del proyecto de Programación 2 entregó una API REST construida con Spring Boot que centraliza la persistencia en MySQL y los servicios de compilación y ejecución de código Java con guali-dev.jar. Sobre esa base, la Fase 3 incorpora un cliente Android que permite al estudiante abrir lecciones, leer su contenido, escribir código, compilarlo y ejecutarlo desde un teléfono o emulador.

El cliente no se conecta a MySQL ni compila código localmente. Toda operación de datos y toda ejecución se realizan en el servidor de la Fase 2 a través de HTTP y JSON. Esta separación mantiene una única fuente de verdad para las lecciones, el historial y la configuración del JDK, y permite que el teléfono funcione incluso sin un entorno de desarrollo Java instalado.

Este documento describe la arquitectura, la interfaz, la integración con la API, la instalación, la compilación y las pruebas del cliente Android. Incluye además la URL pública del tutorial en Markdown solicitada por el enunciado.

## 1.1 Propósito
Documentar de forma completa y reproducible la solución de la Fase 3, de manera que el catedrático y cualquier desarrollador puedan comprender la arquitectura, instalar el proyecto, ejecutarlo y verificar su funcionamiento sin asistencia del autor.

## 1.2 Alcance
- Cliente Android en Java con Android Studio, Gradle y Material 3.
- Barra de menú, título de la lección activa, panel de la lección, editor de código, consola y botones Compilar y Ejecutar.
- Consumo de la API REST de la Fase 2 para lecciones, historial, configuración del JDK y ejecución de código.
- Diseño adaptable a orientación vertical y horizontal.
- Modo de demostración sin conexión con un catálogo local de cuatro lecciones.
- Pruebas unitarias de la lógica de objetivos.
- Tutorial paso a paso publicado en GitHub con capturas de pantalla.

> La Fase 3 no incluye autenticación de usuarios ni publicación en Google Play. La aplicación está pensada para ejecutarse en la red local del estudiante o del laboratorio.

## 3.1 Justificación de Java y Android nativo
Se eligió Java porque es el lenguaje del curso y de las fases anteriores. Android nativo con Views permite construir la interfaz solicitada sin introducir Kotlin ni Jetpack Compose, mantiene continuidad con el cliente Swing de la Fase 2 y facilita la reutilización de los modelos y de la lógica de evaluación de objetivos.

## 3.2 Justificación de HttpURLConnection y Gson
HttpURLConnection viene incluido en Android y evita agregar una biblioteca HTTP adicional. Gson convierte los objetos JSON de la API en clases Java con una configuración mínima. Ambos mantienen el APK liviano y son suficientes para el alcance del proyecto.

## 3.3 Justificación del modo de demostración
La compilación y la ejecución requieren el servidor, pero la interfaz debe poder revisarse aunque la API no esté iniciada. Por eso se incluye un catálogo local en assets/demo/lecciones.json que permite recorrer la pantalla, abrir lecciones y ver el editor. En ese modo los botones de compilación y ejecución permanecen deshabilitados.

# 4. Arquitectura de la solución
El cliente aplica el patrón Modelo-Vista-Controlador y se comunica con la API REST de la Fase 2 mediante HTTP y JSON. La API es el único componente que accede a MySQL y el único que ejecuta guali-dev.jar con el JDK 25.

![Arquitectura del cliente Android](C:\Users\asop2\Downloads\fase 3\docs\img\09-arquitectura.png)

## 4.1 Capa de vista
Está formada por MainActivity, HistorialActivity y AyudaActivity, junto con los layouts XML, EditorCodigoView, Consola, AdaptadorHistorial y DialogoConfiguracion. La vista construye los componentes, muestra los datos y notifica al controlador las acciones del usuario. No contiene llamadas HTTP ni SQL.

## 4.2 Capa de control
MainActivity coordina el flujo principal: carga las lecciones al iniciar, responde a los menús y botones, invoca ApiCliente a través de TareaAsincrona y actualiza el estado de la interfaz. HistorialActivity y AyudaActivity controlan sus propias pantallas. DialogoConfiguracion coordina la configuración de la API y del JDK.

## 4.3 Capa de modelo
Los paquetes modelo y util contienen las clases que representan el dominio: Leccion, LeccionResumen, HistorialRegistro, ResultadoCompilacion, ResultadoEjecucion, EstadoJdk, ObjetivoLeccion y EstadoLeccion. También incluyen EvaluadorObjetivos, que decide cuándo se cumple el objetivo de una lección, y Formato, que presenta fechas y horas.

## 4.4 Capa de servicios y datos
ApiCliente encapsula las peticiones HTTP, Preferencias guarda la dirección de la API en SharedPreferences, RepositorioDemo carga el catálogo local y TareaAsincrona ejecuta las operaciones en un hilo secundario. MarcadorMarkdown convierte el contenido Markdown de las lecciones en texto con formato para mostrarlo en la interfaz.

## 4.5 Flujo de una compilación
1. El usuario abre una lección y presiona Compilar.
2. MainActivity valida que haya lección, que no esté en modo demostración, que el JDK esté configurado y que el editor tenga código.
3. TareaAsincrona ejecuta ApiCliente.compilar en un hilo secundario.
4. ApiCliente envía POST /api/v1/ejecucion/compilar con el código en JSON.
5. La API ejecuta guali-dev.jar con el JDK 25 del servidor y devuelve el resultado.
6. MainActivity muestra el resultado en la consola, habilita Ejecutar si fue correcto y evalúa el objetivo de la lección.
7. Si el objetivo se cumple, se actualiza el historial a COMPLETADA mediante PATCH /api/v1/historial/{id}.

## 4.6 Decisiones de diseño
- No compilar en el teléfono: Android no incluye un JDK y la API ya ofrece el servicio de ejecución.
- Separar ApiCliente de las actividades para facilitar pruebas y cambios de transporte.
- Usar TareaAsincrona con ExecutorService y Handler para no bloquear el hilo principal.
- Guardar la dirección de la API en SharedPreferences para cambiarla sin recompilar.
- Usar 10.0.2.2 como dirección por omisión en el emulador.
- Declarar usesCleartextTraffic y network_security_config para permitir HTTP local durante el desarrollo.
- Ofrecer layout vertical y horizontal con los mismos identificadores.
- Incluir un catálogo de demostración para revisar la interfaz sin servidor.
- Invalidar la compilación cuando el código cambia después de compilar.

# 6. Interfaz de la aplicación
La pantalla principal se organiza en cinco franjas: barra de herramientas, barra de menú, título de la lección activa, panel de la lección con editor y consola. Los botones Compilar y Ejecutar están dentro de la tarjeta del editor para mantener el flujo de trabajo.

![Pantalla principal de Práctica de Código](C:\Users\asop2\Downloads\fase 3\docs\img\01-pantalla-principal.png)

## 6.1 Barra de menú
La barra de menú es horizontal y contiene cuatro opciones: Lección, Configuración, Historial y Ayuda. Cada opción abre un PopupMenu con las acciones correspondientes.

| Menú | Acciones |
| Lección | Abrir lección, cerrar lección, copiar código de ejemplo |
| Configuración | Configurar JDK, dirección de la API, recargar lecciones |
| Historial | Ver historial de sesión |
| Ayuda | Ayuda de la aplicación, acerca de |

La barra se implementa con TextViews dentro de un HorizontalScrollView, de modo que se adapta a pantallas angostas. Los ítems tienen ícono, texto y un fondo resaltado cuando el menú está activo.

![Menú Lección desplegado](C:\Users\asop2\Downloads\fase 3\docs\img\02-menu-leccion.png)

## 6.2 Título de la lección activa
Debajo de la barra de menú se muestra el título de la lección abierta con el prefijo "Lección activa:". A la derecha se presentan dos chips: el objetivo de la lección y el estado PENDIENTE o COMPLETADA. Cuando no hay lección, el título indica "Ninguna lección abierta" y el subtítulo invita a seleccionar una.

## 6.3 Panel de la lección activa
El panel contiene el listado de lecciones en un Spinner, el botón Abrir, el título, el objetivo y el contenido Markdown. El contenido se renderiza con MarcadorMarkdown, que reconoce títulos, listas, negritas, código en línea y bloques de código.

El código de ejemplo se extrae del primer bloque ```java del Markdown y se copia al editor al abrir la lección. El botón de copiar permite restaurarlo si el estudiante lo modificó.

## 6.4 Editor de código
EditorCodigoView combina un TextView con los números de línea, un HorizontalScrollView y un EditText monoespaciado. El editor permite desplazamiento horizontal y vertical, mantiene la numeración sincronizada y notifica los cambios para invalidar la compilación anterior.

El encabezado del editor muestra el nombre de la clase compilada o el texto "Sin compilar". El botón de copiar código restaura el ejemplo de la lección.

## 6.5 Consola
La consola es un TextView monoespaciado dentro de un ScrollView. Consola agrega cada mensaje con la hora y un color según el tipo: información, éxito, error, comando y salida del programa. La consola se desplaza automáticamente al final y puede limpiarse con el botón correspondiente.

## 6.6 Botones Compilar y Ejecutar
Compilar envía el código a la API y muestra el resultado. Si la compilación es correcta, guarda el nombre de la clase y habilita Ejecutar. Si el código cambia, la compilación se invalida y Ejecutar se deshabilita hasta compilar de nuevo.

Ejecutar llama a la API con el nombre de la clase compilada y un tiempo límite de 10 segundos. La salida y los errores se muestran en la consola. Un tiempo de espera agotado se informa como error de ejecución.

# 7. Integración con la API REST
ApiCliente encapsula las peticiones con HttpURLConnection y Gson. Todos los métodos son síncronos y se ejecutan desde TareaAsincrona en un hilo secundario. La dirección base se normaliza para eliminar la barra final y se obtiene de Preferencias.

## 7.1 Endpoints utilizados
| Método | Ruta | Uso en el cliente |
| GET | /api/v1/lecciones | Cargar el listado de lecciones |
| GET | /api/v1/lecciones/{id} | Abrir una lección completa |
| GET | /api/v1/historial | Mostrar el historial |
| POST | /api/v1/historial | Registrar la apertura de una lección |
| PATCH | /api/v1/historial/{id} | Marcar la lección como COMPLETADA |
| GET | /api/v1/ejecucion/jdk | Consultar el estado del JDK |
| PUT | /api/v1/configuracion/jdk.ruta | Guardar la ruta del JDK |
| POST | /api/v1/ejecucion/compilar | Compilar el código del editor |
| POST | /api/v1/ejecucion/ejecutar | Ejecutar la clase compilada |

## 7.2 Tiempos de espera
| Operación | Tiempo de conexión | Tiempo de lectura |
| Conexión general | 10 segundos | 20 segundos |
| Compilación | 10 segundos | 150 segundos |
| Ejecución | 10 segundos | 90 segundos |

La compilación tiene un tiempo de lectura mayor porque el servidor debe iniciar javac y resolver las dependencias de guali-dev.jar. La ejecución tiene un tiempo límite adicional de 10 segundos configurado en la solicitud.

## 7.3 Formato de las solicitudes
Registrar una apertura:
```json
{
  "leccionId": 1,
  "leccionNombre": "leccion-01-hola-mundo",
  "objetivo": "COMPILAR_EXITOSO",
  "detalle": null
}
```

Compilar:
```json
{
  "codigo": "public class HolaMundo { public static void main(String[] args) { System.out.println(\"Hola\"); } }"
}
```

Ejecutar:
```json
{
  "nombreClase": "HolaMundo",
  "timeoutSegundos": 10
}
```

Marcar como completada:
```json
{
  "estado": "COMPLETADA",
  "detalle": "Se cumplio el objetivo COMPILAR_EXITOSO al compilar."
}
```

## 7.4 Manejo de errores
ApiCliente lee el cuerpo de error de la API y construye una ApiExcepcion con el código HTTP y el mensaje. Si no hay conexión, informa "No se pudo conectar con <dirección>". MainActivity muestra el mensaje en la consola y, cuando corresponde, activa el modo de demostración.

## 7.5 Configuración del JDK
La ruta del JDK se guarda en la tabla configuracion del servidor. Al abrir el diálogo, el cliente consulta GET /api/v1/ejecucion/jdk. Si el JDK está configurado, muestra la ruta; si no, solicita escribirla. El botón Verificar consulta el estado y el botón Guardar envía la ruta con PUT /api/v1/configuracion/jdk.ruta.

## 7.6 Historial y objetivos
Al abrir una lección se registra una apertura en estado PENDIENTE. Cuando la compilación o la ejecución cumplen el objetivo configurado, el cliente envía PATCH con estado COMPLETADA y un detalle descriptivo. Si la lección ya estaba completada, no se vuelve a actualizar.

| Objetivo | Se cumple cuando |
| COMPILAR_EXITOSO | La compilación termina sin errores |
| COMPILAR_CON_ERROR | La compilación reporta errores |
| EJECUTAR_EXITOSO | La ejecución termina sin errores ni tiempo agotado |
| EJECUTAR_CON_ERROR | La ejecución falla o excede el tiempo límite |

# 8. Modelo de datos del cliente
Los modelos son clases Java simples que Gson convierte desde el JSON de la API. Los nombres de los campos coinciden con el contrato OpenAPI de la Fase 2.

| Clase | Uso |
| LeccionResumen | Datos del listado: id, nombre, título y objetivo |
| Leccion | Lección completa: contenido Markdown y recursos |
| RecursoLeccion | Metadatos de una imagen asociada |
| HistorialRegistro | Registro del historial y su estado |
| EstadoJdk | Ruta y estado de configuración del JDK |
| ResultadoCompilacion | Éxito, salida y nombre de la clase |
| ResultadoEjecucion | Éxito, salida, errores y tiempo agotado |
| SolicitudCompilacion | Cuerpo con el código a compilar |
| SolicitudEjecucion | Cuerpo con la clase y el tiempo límite |
| SolicitudHistorial | Cuerpo para registrar una apertura |
| ActualizacionHistorial | Cuerpo para cambiar estado y detalle |
| ValorConfiguracion | Cuerpo con el valor de una clave |
| ErrorRespuesta | Cuerpo uniforme de error de la API |
| ObjetivoLeccion | Enum de objetivos con etiquetas legibles |
| EstadoLeccion | Enum COMPLETADA y PENDIENTE |

LeccionResumen no incluye el campo recursos. El listado de la API devuelve un entero con el número de recursos, mientras que el detalle devuelve un arreglo. Gson ignora el entero del resumen y mapea el arreglo al campo recursos de Leccion, lo que evita conflictos de herencia.

# 9. Instalación y configuración
## 9.1 Requisitos previos
- JDK 25 instalado y JAVA_HOME configurado en el servidor.
- Android Studio con Android SDK 35 y Build-Tools 35.
- Emulador con imagen API 35 o dispositivo físico con depuración USB.
- API REST de la Fase 2 en ejecución.
- MySQL 8 con la base de datos de la Fase 2.
- Git 2.55 o superior para publicar el tutorial.

## 9.2 Verificación del entorno
| Herramienta | Comando | Resultado esperado |
| JDK | java -version | Versión 25.x |
| Compilador | javac -version | Versión 25.x |
| Gradle wrapper | gradlew --version | Gradle 8.9 |
| Android SDK | SDK Manager | Platform 35 instalada |
| Maven | mvn -version | 3.9.12 o superior |
| MySQL | mysql --version | 8.0.x |
| Git | git --version | 2.55.x |

## 9.3 Abrir el proyecto
1. Inicie Android Studio.
2. Elija Open y seleccione la carpeta android del proyecto.
3. Espere la sincronización de Gradle.
4. Si aparece el aviso de SDK, copie local.properties.example a local.properties y ajuste sdk.dir con la ruta del SDK.
5. Verifique en SDK Manager que esté instalada la plataforma 35.

## 9.4 Iniciar la API de la Fase 2
Desde la carpeta backend de la Fase 2:
```powershell
java -jar target\proyecto-fase-2-backend.jar
```
Verifique la API:
```powershell
curl.exe http://localhost:8080/api/v1/salud
```
La API debe devolver estado OK y la base de datos disponible. Si la API no está iniciada, la aplicación funciona en modo de demostración, pero no puede compilar ni ejecutar.

## 9.5 Configurar la dirección de la API
En el emulador, la dirección por omisión es http://10.0.2.2:8080. En un dispositivo físico debe usarse la IP del equipo en la red local, por ejemplo http://192.168.1.20:8080. La dirección se cambia desde Configuración > Dirección de la API y se guarda en SharedPreferences.

## 9.6 Configurar el JDK del servidor
1. Abra Configuración > Configurar JDK.
2. Escriba la ruta absoluta del JDK 25 en el servidor. Ejemplo: C:\Program Files\Eclipse Adoptium\jdk-25.0.3.9-hotspot.
3. Presione Verificar para consultar el estado.
4. Presione Guardar. La ruta se envía a la API y queda disponible para guali-dev.jar.

> La ruta debe existir en el equipo donde corre la API, no en el teléfono. El teléfono no puede explorar el sistema de archivos del servidor.

# 10. Compilación y ejecución
## 10.1 Compilar el APK
Desde la carpeta android:
```powershell
.\gradlew.bat assembleDebug
```
El APK se genera en app/build/outputs/apk/debug/app-debug.apk. Para una versión de entrega:
```powershell
.\gradlew.bat assembleRelease
```

# Anexo B. Solución de problemas
| Síntoma | Causa probable | Solución |
| No se pudo conectar con la API | El backend no está iniciado o la URL es incorrecta | Inicie el backend y revise Configuración > Dirección de la API |
| JDK no configurado | Falta la clave jdk.ruta en la API | Guarde la ruta del JDK 25 desde Configurar JDK |
| Compile el código actual antes de ejecutarlo | El código cambió después de compilar | Presione Compilar de nuevo |
| Cleartext HTTP traffic not permitted | Falta la configuración de red | Verifique usesCleartextTraffic y network_security_config.xml |
| El emulador no conecta con localhost | localhost apunta al emulador | Use 10.0.2.2 |
| El dispositivo físico no conecta | IP o firewall | Use la IP de la LAN y permita el puerto 8080 |
| Gradle no descarga dependencias | Sin Internet o proxy | Revise la conexión y el proxy de Android Studio |
| SDK location not found | Falta local.properties | Copie local.properties.example y ajuste sdk.dir |
| La aplicación se abre en modo demostración | La API no responde | Inicie la API y presione Recargar lecciones |
| No aparece la clase compilada | La compilación falló | Revise los errores de la consola y corrija el código |
